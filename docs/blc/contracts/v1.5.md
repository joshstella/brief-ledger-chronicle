# Contract v1.5 — the briefs convention

**Status:** current

Supersedes [v1.4](v1.4.md). Clauses BRIEFS-1 through BRIEFS-11 are unchanged in text, tag,
check and directory. **This version adds no clause.** What changed is the recovery rule for
concurrent filing, below — which is normative text people follow, and editing it inside a
published version would make every citation of v1.4 silently wrong.

What this repository guarantees about the structure of `docs/blc/briefs/`. See
[README](README.md) for how to read a clause and what a Contract will not do.

## Scope of this version

Version 1.5 covers the structure of `docs/blc/briefs/` only. It says nothing about process —
which skills gate `main`, whether tests are required — even though those rules are stated in
the present tense elsewhere in this repository. That silence is deliberate. This document
does not claim to be the only place rules live.

**What changed in 1.5 is a rule that was wrong, and a limitation that was understated.** No
clause moved. v1.4 recovered a serial collision by giving the number to whichever brief
reached `main` first. The first collision in the field showed what that rule measures. The
contributor who filed first, and followed the procedure, lost the serial — because pushing to
`main` needed an access level they did not have, so their claim could only reach a branch. The
contributor who could push kept it. A rule that reads as a neutral tiebreak and is really a
test of permissions is worse than no rule, because it settles the argument in the wrong
direction while looking principled. The rule now turns on when each brief was filed, which is
written in the record already and asks nothing about who can push.

The limitation also understated the case. v1.4 described recovery on a branch before it
merged. In the collision that happened, both briefs had already merged, so there was no losing
branch to fix and the published procedure had no step for the state the repository was in.

**What is added in 1.4 is one clause, and it reads a file the Contract already reads.**
`BRIEFS-11` asks a `ledger.md` whose status line says the brief is closed to carry the date
it closed. It widens nothing: `BRIEFS-9` and `BRIEFS-10` already read `ledger.md`, and this
asks a third question of the same file. It is `[judgment]`, so it reports and never blocks —
which is not a courtesy to other repositories but the only honest tag for it. Half the closed
briefs in the repository that wrote this clause do not satisfy it, and they are record, which
this project does not rewrite to make a later rule true.

**What moved in 1.3 is the root, and only the root.** Everything the toolkit writes into a
repository now sits under `docs/blc/`, so a project's own `docs/` holds nothing of ours beside
it. The clauses read the same files in the same way. A citation of `BRIEFS-n` means the same
rule in v1.2 and v1.3, applied to a different directory. The version still changes, because the
directory is part of every clause's meaning, and a published version edited in place would
make every citation of it silently wrong.

**What widened in 1.2 is which file the clauses read.** Clauses 1 through 8 govern the briefs
directory and `brief.md`: the record is well formed. `BRIEFS-9` and `BRIEFS-10` are the first
clauses to read `ledger.md`, which moves the Contract from "the record is well formed" to "the
ledger is internally consistent". That is a real widening and it is taken deliberately, not as
a side effect of adding a ninth item. A brief that has not been started has no ledger, and both
new clauses pass it silently rather than treating absence as a violation.

**Every clause in version 1.5 is checked by `tools/validate-briefs.sh`.** No clause carries a
review date, because none is unchecked and a CI run is a better date than a hand stamp.

Three limits on that claim, stated because a validator implying coverage it lacks is the
defect this document exists to prevent.

**The script no longer travels alone.** Version 1.1 said the script "travels with this
document, so a repository that holds the Contract also holds the check". That stopped being
true in 1.2. `tools/validate-briefs.sh` now sources `tools/lib/status-line.sh`,
`tools/lib/phase-row.sh` and `tools/lib/identity-line.sh`, because the clauses below must read
a ledger and an identity line exactly as the other tools read them — `tools/open-briefs.sh`,
`tools/list-briefs.sh` and `tools/jira-csv.sh` — and independent readers of one format are the drift this Contract was extracted to end.
The check is now a script plus three libraries. v1.2 said two, and was out of date by the time
it was superseded. The installer ships all of them. A validator that cannot load a library
exits 2 rather than 0, so a broken checker is never read as a clean tree.

`BRIEFS-8`, `BRIEFS-9`, `BRIEFS-10` and `BRIEFS-11` are checked but never block. The validator prints them
and exits zero. For `BRIEFS-8` the reason is that a retired serial is a question for a human.
For the two new clauses the reason is stated under them.

**Holding the script is not running it.** Where no continuous integration job calls it,
these clauses are exactly as reliable as the people who follow them.

**Every clause in version 1.5 is scope `both`**, so in this version the field discriminates
nothing. It is stated per clause anyway, because it starts to carry weight the moment a
second namespace arrives, and because a field introduced later reads as a change in meaning
rather than a change in coverage.

## Clauses

### BRIEFS-1 — entries are briefs or known non-numbered files

`[defect]` · scope `both` · checked: `tools/validate-briefs.sh`

Every entry in `docs/blc/briefs/` is either a `NNNN-slug/` folder or a known non-numbered entry
(`_drafts/`, `README.md`).

### BRIEFS-2 — slug and serial shape

`[defect]` · scope `both` · checked: `tools/validate-briefs.sh`

Slugs match `^[a-z0-9-]+$`. Serial prefixes are exactly four digits.

### BRIEFS-3 — serials are unique

`[defect]` · scope `both` · checked: `tools/validate-briefs.sh`

No two folders share an `NNNN`.

### BRIEFS-4 — every brief folder holds a brief

`[defect]` · scope `both` · checked: `tools/validate-briefs.sh`

Every `NNNN-slug/` contains a `brief.md`.

### BRIEFS-5 — the identity line is well formed

`[defect]` · scope `both` · checked: `tools/validate-briefs.sh`

Each `brief.md` carries an identity line whose `Serial` matches its folder, with `Created`
(ISO-8601 UTC), `Author` (email-shaped), and `Depends on`.

### BRIEFS-6 — no dangling dependencies

`[defect]` · scope `both` · checked: `tools/validate-briefs.sh`

Every `Depends on: #NNNN` references an existing serial.

### BRIEFS-7 — drafts are unnumbered

`[defect]` · scope `both` · checked: `tools/validate-briefs.sh`

Nothing in `_drafts/` has a four-digit-prefixed name.

### BRIEFS-8 — serials are contiguous

`[judgment]` · scope `both` · checked: `tools/validate-briefs.sh` (never blocks)

Serials run contiguously from `0001`. A gap is surfaced, not blocked: a removed brief
legitimately retires its number.

### BRIEFS-9 — a declared phase is findable in the phase table

`[judgment]` · scope `both` · checked: `tools/validate-briefs.sh` (never blocks)

Every phase index a ledger's status line declares has a matching row in that ledger's phase
table. A phase index is a single lowercase letter, or digits.

A ledger states its phases twice — once compactly in the status line, once in full in the
phase table — and those two statements can disagree. When they do, a reader is told the work
is at phase `c` and finds nothing called `c` to read.

**What the clause examines.** A token is considered only if it contains a colon, which is what
makes a phase entry a phase entry. This is deliberately narrow: real status lines in this
repository carry free text such as `done(commit 92a7168)`, and a clause that parsed by
position would report those as broken phases.

Of the tokens that do contain a colon, exactly two outcomes are reported:

- an id that is a phase index, with no matching row in the phase table;
- an id that is entirely lowercase letters but is not a single letter — `bc:done`,
  `https://example.com/x` — reported as a token the reader could not parse.

Everything else is silent. An id mixing letters and digits (`a1:done`), an uppercase id
(`A1:done`), and a timestamp (`2026-01-01T00:00:00Z`) are not treated as phase entries at
all. This is the deliberate boundary of the clause rather than an oversight: status lines and
the prose beside them contain colons for reasons that have nothing to do with phases, and a
clause that complained about all of them would be noise a reader learns to skip, which is the
failure mode this Contract exists to avoid.

The cost is stated plainly: `a1:done` written where `a:done` was meant is a typo this clause
does not catch, and it is a likely typo rather than a contrived one.

The boundary is drawn where it is because excluding every id that mixes letters and digits was
the simplest way to exclude timestamps. It is wider than it needs to be. A narrower rule —
lowercase letters followed by digits — would catch `a1:done` while still excluding a timestamp,
which begins with a digit, and an uppercase id. That rule is not in this version. It is
recorded here rather than left implicit so that the limit reads as a boundary someone chose
and can move, not as evidence that no better rule exists.

It never blocks. This toolkit installs into repositories whose ledgers it did not write, and
the failure modes are not symmetric: a `[judgment]` that should have gated costs a warning
nobody acted on, while a `[defect]` that should have reported breaks someone else's build on
the day they upgrade, for a ledger that was legal when they wrote it.

### BRIEFS-10 — a ledger's frontmatter and code fences are closed

`[judgment]` · scope `both` · checked: `tools/validate-briefs.sh` (never blocks)

A `ledger.md` does not end inside an unterminated `---` frontmatter block or an unterminated
code fence.

This is separate from `BRIEFS-9` rather than folded into it because the two describe different
faults. `BRIEFS-9` says the ledger's two statements disagree; `BRIEFS-10` says the file's
structure is broken, which makes every statement in it unreliable, including the one
`BRIEFS-9` reads. Reporting them under one id would tell a reader the phases disagree when the
real answer is that nothing in the file can be trusted to parse.

Frontmatter runs from a `---` on line 1 to the next `---`. A fence delimiter inside that block
is inert, because the interior is YAML. This matches what every markdown tool does, and the
behaviour is pinned by a test rather than left to be rediscovered.

It never blocks, for the reason given under `BRIEFS-9`, and one more: an unclosed fence is
usually a document someone is midway through writing.

### BRIEFS-11 — a closed brief records when it closed

`[judgment]` · scope `both` · checked: `tools/validate-briefs.sh` (never blocks)

A `ledger.md` whose status line gives the brief the state `done` carries a `**Closed:**`
line.

The state is read from the status line, not from the `**Status:**` field. A ledger carries
both and they can disagree, so the clause names which one it asks. The status line is the
statement every tool here already parses — `open-briefs.sh`, `list-briefs.sh`, `jira-csv.sh`
and this validator — through one shared reader. A clause that read the prose field instead
would make the gate the only reader in the repository answering "is this closed?" from a
different place, which is the drift `BRIEFS-9` and `BRIEFS-10` were written to end.

It asks closed briefs only. A brief in flight has no close to record, and a clause that
reported every open brief would be noise in a judgment whose only power is being read.

The `**Closed:**` line is read outside code fences and outside frontmatter, by the same scan
that finds the status line. A ledger showing the field in a fenced example is documenting the
format, not recording its own close, and a reader matching the raw file cannot tell the two
apart. The status line already carried this fault and lost it in review before any ledger met
it; this clause is held to the same standard rather than left to learn it later.

The date is not checked for shape, and that is a deliberate stop rather than an omission.
The failure this clause addresses is a brief that closed and said nothing about when — not a
brief that wrote the date in an unexpected format. A format rule would also have to decide
what the date of a close *is*, and the honest answer is that only the person closing it
knows. Deriving one from a merge commit was considered and rejected: that is the date a
branch landed, and writing it into the record would make the record assert something nobody
said.

It never blocks, for the reason given under `BRIEFS-9`, and because the repository that
wrote the clause fails it sixteen times. Those ledgers are record. They are reported and
left alone.

## Known limitation — concurrent filing

`blc-create-brief` asks `tools/next-serial.sh` for the next serial, then writes the folder. A
second step increments until that path is free on this checkout. That step closes a stale read
on one machine. It does not close two machines.

Allocation against the pushed remote **is built** as of this version. `tools/next-serial.sh`
lists `docs/blc/briefs/` on every `origin` branch as well as locally, so a serial filed on a
branch counts as taken whether or not it has merged. That is a real narrowing, and it would
have caught the collision described below.

**It does not close the race, and nothing should be read as saying it does.** Answering is not
claiming. `blc-create-brief` publishes nothing, so two checkouts can fetch the same `origin`
seconds apart, both see the same highest serial, and both pick the next one. Each passes its
own guard. Each can claim the same serial, which would break `BRIEFS-3`. Solo, this never
fires. Two people filing two briefs can still hit it.

Closing it for real means publishing a reservation before the other reader runs — a push at
filing time. This project does not do that, and the collision below is part of why: **every
mechanism this toolkit has for claiming a serial requires pushing to `main`.** The ledger
write at filing does. The `docs/blc/state/` declaration does. A contributor who cannot push to
`main` cannot publish a claim by any route offered here, so the step that would have prevented
the collision was not available to the person who needed it.

### Recovery

**The brief with the earlier `Created` stamp keeps the serial.** That stamp is in the identity
line, written when the draft was written, and it answers the only question that matters: which
filing came first. It asks nothing about who can push.

The other brief renumbers. Change its folder name, its identity line, its ledger status line,
any inbound `Depends on` that meant it, and its PR title if it has one. Leave its `Created`,
`Author` and `Depends on` values alone — the point of the rule is that the original filing
stands.

**If the loser has not merged,** renumber on its own branch, not by rewriting history on
`main`.

**If both have already merged,** which is the case this rule was written from, there is no
losing branch left. Renumber on a new branch through the normal review and merge, titled for
the repair rather than for a phase. Do not rewrite `main`. Until it lands, `BRIEFS-3` reports
the duplicate as a `[defect]` and the gate exits non-zero, which is correct and is the signal
that the repair is outstanding.

**If the two stamps are equal, or one is missing,** the contributors decide between them and
record the decision in both ledgers. A same-second tie is vanishingly rare, and an invented
fallback — lowest email, fewest inbound links, least work to move — would look objective while
settling a question it has no standing to settle. Naming it a human decision is the honest
answer, and writing it into both ledgers is what keeps it from being re-argued.

### What this rule was written from

Two contributors filed two different briefs under the same serial on the same day, eighty
minutes apart, and both reached `main`.

The first filed at 02:46 and pushed to a branch, because `main` in that project needed an
access level they did not have. Their claim existed only on that branch. The second filed at
04:06 against a trunk whose briefs directory still ended one below, and which could not see
the branch. Neither read a stale directory. Both read a true one that did not contain the
other. The second contributor could push to `main` and did. The first contributor's work
merged more than seven hours later, by which time `main` held two folders on one serial.

Under v1.4's rule the second brief kept the serial, and the contributor who filed first and
followed the procedure was the one who had to move. Under this rule the first filing keeps it.
